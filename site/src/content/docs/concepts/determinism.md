---
title: Determinism
description: What a semis run reproduces in each FK mode, and why a scenario applies once, to a reset database
---

The same scenario, seed and schema produce the same rows. What that guarantees depends on
the mode: a prep-seed run is byte-reproducible, and a read-back run is reproducible except
for the integers PostgreSQL assigns.

| Component | Deterministic because |
|---|---|
| The UUID of a row | table code, scenario id, version and sequence, all fixed by the scenario and the row's position |
| Faker values | one seed per run, taken from the scenario |
| Dates and times | drawn from a fixed window, 1970 to 2026, never up to the moment of the run |
| Table order | confiture's dependency order: among the tables ready at each step, the first by schema and name |
| Column order | the order the schema declares them |
| The schema itself | the [schema pin](/concepts/schema-pins/) |

## Prep-seed is byte-reproducible

Every value in a prep-seed file is semis', including the foreign keys, which carry UUIDs.
In the project from [Getting started](/getting-started/), two runs write the same files:

```bash
semis seeds scenarios/continents.yaml -o run-1
semis seeds scenarios/continents.yaml -o run-2
diff -r run-1 run-2
```

`diff` prints nothing. The same holds on any machine, so a seed file can be committed,
reviewed in a pull request, and checked in CI: a change to the generated bytes is a change
to the scenario, the schema, or semis.

A run may take another seed, locale or scenario id without editing the file, and says so:

```bash
semis seeds scenarios/continents.yaml -o run-3 --seed 7
```

```text
scenario continents runs with seed 7, not 42, for this run
scenario continents is unpinned: its schema is not checked
wrote 001_prep_seed.tb_continent.sql  7 rows
wrote 002_prep_seed.tb_country.sql    21 rows
wrote run-3/schema_pin.yaml: copy it into the scenario to pin its schema
```

## Read-back is reproducible except the keys

A read-back seed file carries the integer keys PostgreSQL gave the parent rows, drawn from
an identity sequence whose state semis does not control. The same seed file, applied to a
fresh database and again after a plain `TRUNCATE`, points at different integers:

```text
fresh database         -> fk targets: [1, 2]
after TRUNCATE, re-run -> fk targets: [3, 4]
```

A plain `TRUNCATE` does not reset an identity sequence. `TRUNCATE … RESTART IDENTITY`
does, and a project that restarts its identities gets byte-identical read-back output.
The shape is identical either way: the same children point at the same parents, because
each key is learned by joining on the UUID. A read-back seed file is an artifact of a run,
not a reviewable document.

## A scenario applies once

A row's UUID is a function of its scenario and its position, not of the run, so a scenario
applied twice into one database would write the same values again. semis tracks nothing
of what it has applied: a scenario is a statement about what a database contains, and
PostgreSQL knows whether it already does. Before anything is written, `semis apply` asks
it, one query per table on the scenario's UUID range, and refuses. The check skips a table
with no `id` column, or whose `id` is not a uuid, since it has no range to ask:

```bash
semis apply scenarios/minimal_seed.yaml -o db/seeds/again --database-url postgresql:///myproject_dev
```

```text
scenario minimal_seed is already applied: prep_seed.tb_continent holds its rows
Hint: A scenario applies once, to a reset database. Reset it with psql -c 'TRUNCATE "catalog"."tb_continent", "prep_seed"."tb_continent", "catalog"."tb_country", "prep_seed"."tb_country" RESTART IDENTITY', or recreate the database, then apply again.
```

To apply it again, reset the run's tables with the hint's statement, or recreate the
database. The statement empties those tables whole, other scenarios' rows and rows the
schema's DDL inserted included, and no other table: every name is quoted, and there is no
`CASCADE`.

```bash
psql -d myproject_dev -c 'TRUNCATE "catalog"."tb_continent", "prep_seed"."tb_continent", "catalog"."tb_country", "prep_seed"."tb_country" RESTART IDENTITY'
semis apply scenarios/minimal_seed.yaml -o db/seeds/again --database-url postgresql:///myproject_dev
```

When a table the run does not write has a foreign key into one of them, PostgreSQL
refuses the statement and empties nothing:

```text
ERROR:  cannot truncate a table referenced in a foreign key constraint
DETAIL:  Table "tb_city" references "tb_country".
HINT:  Truncate table "tb_city" at the same time, or use TRUNCATE ... CASCADE.
```

Whether that table's rows may go too is yours to decide: add it to the statement, or
recreate the database.

`RESTART IDENTITY` matters in read-back: a plain `TRUNCATE` keeps the identity sequences
where they were, so the keys differ from the first run's, as above.

There is no upsert, by design. `ON CONFLICT DO NOTHING` would apply a scenario that has
drifted from the rows it once wrote, and say nothing about it. The check is per scenario:
the `identifier` slug and the UUID both carry the scenario id, so two different scenarios
share a database, and a run under another `--scenario-id` applies beside the first.
